# Архитектурный статус Gonflict

Документ фиксирует текущее состояние архитектуры проекта и приоритетные направления для дальнейшего развития. Проект следует принципам Clean Architecture и поддерживает четкое разделение на Presentation, Application, Domain и Infrastructure.

## Итоговая оценка

| Аспект | Оценка | Комментарий |
| --- | --- | --- |
| Слоевость и зависимостей | 5/5 | Зависимости направлены внутрь, слои изолированы интерфейсами |
| Use cases | 4/5 | Stateless, хорошо сегментированы; требуется контроль новых сценариев |
| Коллизии и физика | 5/5 | Сервисы коллизий отделены, покрыты тестами |
| Работа с ресурсами | 4/5 | Репозитории оформлены, нужна документация по расширению ассетов |
| Оркестрация состояний | 4/5 | App и состояния разделены, но требуется доработка при появлении меню/HUD |
| Тестирование | 3/5 | Сервисы покрыты тестами, остальной код требует расширения покрытия |

**Итог:** архитектура устойчивая, допущенные компромиссы контролируемы. Основное внимание при развитии следует уделять UI/UX и новым игровым механикам, чтобы не допустить эрозии слоев.

## Сильные стороны

- Use cases разбиты по областям ответственности: танки, пули, карта, HQ, AI, коллизии.
- Вся работа с ассетами проходит через репозитории, что упрощает добавление ресурсов.
- Сервисы коллизий вынесены в `internal/services/collision_services/` и покрыты unit-тестами.
- Структуры домена (`internal/types`) не зависят от внешних слоев.
- Сессии разделены на игровой (`GameSessionEntity`) и поуровневый (`StageSessionEntity`) уровни, что упрощает управление прогрессом.
- `App` управляет жизненным циклом зависимостей и состояниями, соблюдая Dependency Inversion.
- Экран выбора уровня вынесен в отдельный адаптер: он поддерживает подсветку активных пунктов меню, выбор числа игроков, максимального количества активных врагов и централизованные подсказки, оставаясь тонким слоем Presentation.

## Области внимания

1. **Состояния и UI**
   - При добавлении HUD, меню и экранов Game Over важно сохранить Presentation слой тонким и не переносить логику в адаптеры.
   - Планируется расширение `GameSessionEntity` для учета очков и жизней, `StageSessionEntity` отвечает за лимиты врагов (включая `maxActiveEnemies`), прогресс уровня и количество игроков.

2. **Новые use cases**
   - Power-ups, волны врагов и система прогрессии потребуют новых use cases. Соблюдайте принцип "один use case — одна ответственность".
   - Рассмотрите использование фасадов только на уровне состояний, избегая "god"-объектов. Опирайтесь на локальные сущности сессий (game/stage), чтобы не раздувать состояние.

3. **Репозитории и ресурсы**
   - При добавлении новых категорий ресурсов сначала определяйте интерфейс. Не допускайте чтения файлов в Presentation/Application слоях.

4. **Тестирование**
   - Покрытие бизнес-логики (use cases) ограничено. При добавлении новых сценариев пишите unit-тесты вокруг чистых сервисов и use cases.
   - Подумайте о smoke-тестах состояний игры после появления новых экранов.

## История ключевых улучшений

- Use cases танков разделены на `Common`, `Actions`, `Lifecycle`, `Render`.
- Внедрены интерфейсы для всех use cases и сервисов, что позволило убрать прямые зависимости.
- Реализован `TankBrakingService` с отдельными тестами.
- Добавлены unit-тесты для `StageSessionEntity`, покрывающие базовые сценарии прогресса уровня.
- Реализован выбор максимального количества активных врагов в меню с сохранением в `StageSessionEntity` и применением при спавне врагов.
- Создана единая точка отрисовки `StageRendererAdapter`, концентрирующая всю графику уровня и работающая через интерфейсы use cases.
- Архитектура AI разделена на `LuaEngine`, `AITypeConverter`, `AIUseCases`.
- Добавлены `HQUseCases` и анимации взрыва базы.
- Метод `SyncAnimationWithState` перемещен из `TankCommonUseCases` в `TankRenderUseCases`, что улучшило разделение ответственности между слоями.
- Метод `GetTankAnimationName` перемещен в `TankEntity`, следуя принципам Domain-Driven Design.
- Запрещены сеттеры для зависимостей между use cases — все зависимости передаются через конструкторы (`New*`).

## Рекомендации при разработке

- Новые зависимости добавляйте через конструкторы `New*` и прокидывайте через интерфейсы из каталога `internal/interfaces`.
- **Запрещено создавать методы-сеттеры (`Set*`) для установки зависимостей от других use cases или сервисов в use cases.** Все зависимости должны передаваться через конструкторы.
- Проверяйте компиляцию (`go build ./...`) и линтер (`just lint`) после архитектурных изменений.
- Обновляйте документацию и диаграммы, если меняется состав слоев или поток данных.

Поддержание дисциплины в слоях — ключ к тому, чтобы дальнейшее расширение Gonflict оставалось предсказуемым и управляемым.
