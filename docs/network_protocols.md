## 🏗️ Архитектуры сетевых игр

### 1. Клиент-серверная архитектура (Client-Server)

**Описание:** Один сервер авторитетен для всех игровых решений.

**Преимущества:**
- Централизованная валидация (защита от читов)
- Единая точка истины
- Легче масштабировать
- Предсказуемая производительность

**Недостатки:**
- Требует выделенный сервер
- Сервер становится узким местом
- Стоимость инфраструктуры

**Когда использовать:**
- Многопользовательские игры с важной соревновательной составляющей
- Игры с постоянным миром
- Игры, требующие высокой защиты от читов

**Схема:**
```
Клиент 1 ──┐
Клиент 2 ──┤
Клиент 3 ──┼──> Сервер (авторитетный)
Клиент 4 ──┘
```

### 2. P2P архитектура (Peer-to-Peer)

**Описание:** Каждый клиент подключен напрямую к другим клиентам.

**Преимущества:**
- Нет необходимости в сервере
- Низкая латентность (прямое соединение)
- Меньше затрат на инфраструктуру

**Недостатки:**
- Уязвимость к читам
- Сложнее синхронизировать состояние
- Проблемы с NAT и файрволами
- Нет централизованной авторизации

**Когда использовать:**
- Казуальные многопользовательские игры
- Локальные сетевые игры (LAN)
- Кооперативные игры с доверенными игроками

### 3. Гибридная архитектура (Dedicated Server + P2P)

**Описание:** Комбинация авторитетного сервера и прямых соединений для определенных данных.

**Примеры использования:**
- Сервер обрабатывает игровую логику и валидацию
- P2P используется для голосового чата или вспомогательных данных

## 🔌 Выбор протокола

### TCP vs UDP

#### TCP (Transmission Control Protocol)

**Характеристики:**
- Гарантированная доставка пакетов
- Гарантированный порядок доставки
- Автоматическая повторная передача потерянных пакетов
- Управление потоком данных

**Преимущества:**
- Надежность доставки
- Простота использования
- Встроенная проверка ошибок

**Недостатки:**
- Высокая латентность (ожидание подтверждений)
- Проблемы при потере пакетов (head-of-line blocking)
- Медленная адаптация к изменениям сетевых условий

**Когда использовать:**
- Важные сообщения (вход/выход игроков, окончание игры)
- Игры с пошаговой механикой (шахматы, карты)
- Игры, где порядок событий критичен

#### UDP (User Datagram Protocol)

**Характеристики:**
- Минимальная латентность
- Нет гарантии доставки
- Нет гарантии порядка
- Нет контроля потока

**Преимущества:**
- Низкая латентность
- Быстрая адаптация к сетевым условиям
- Подходит для частых обновлений состояния

**Недостатки:**
- Потеря пакетов может вызвать проблемы
- Нужно реализовывать надежность вручную (для критичных данных)
- Сложнее обработка ошибок

**Когда использовать:**
- Быстрые экшн-игры (шутеры, гоночные игры)
- Частые обновления позиций (30-60 Hz)
- Когда потеря одного пакета не критична

### Гибридный подход

**Практика:** Использовать оба протокола для разных типов данных.

```go
// TCP для критичных команд
type GameCommand struct {
    PlayerJoin    // TCP
    PlayerLeave   // TCP
    GameStart     // TCP
    GameEnd       // TCP
}

// UDP для частых обновлений
type GameUpdate struct {
    PositionUpdate  // UDP
    MovementInput   // UDP
    StateSnapshot   // UDP
}
```

## 📐 Проектирование протокола

### 1. Бинарные протоколы vs Текстовые протоколы

#### Бинарные протоколы

**Преимущества:**
- Минимальный размер пакетов
- Быстрая сериализация/десериализация
- Эффективное использование пропускной способности

**Недостатки:**
- Сложнее отладка
- Менее читаемый формат
- Сложнее версионирование

**Формат:**
```
[Header: 4 байта][Type: 1 байт][Payload: N байт]
```

#### Текстовые протоколы (JSON, XML)

**Преимущества:**
- Легко читаемый формат
- Простая отладка
- Гибкое версионирование

**Недостатки:**
- Больший размер пакетов
- Медленнее парсинг
- Больше трафика

**Рекомендация:** Использовать бинарные протоколы для production, JSON для отладки и разработки.

### 2. Структура пакета

**Базовая структура:**
```
┌─────────────────┐
│   Header (4b)   │  Magic number или размер пакета
├─────────────────┤
│   Type (1b)     │  Тип сообщения
├─────────────────┤
│  Sequence (2b)  │  Номер последовательности (для UDP)
├─────────────────┤
│   Payload (N)   │  Данные сообщения
└─────────────────┘
```

**Пример (бинарный протокол):**
```go
type PacketHeader struct {
    Magic   uint16  // Идентификатор протокола
    Type    uint8   // Тип пакета
    Length  uint16  // Длина payload
}

type PacketType uint8

const (
    PacketTypePosition PacketType = iota
    PacketTypeInput
    PacketTypeState
    PacketTypeCommand
)
```

### 3. Версионирование протокола

**Практика:** Включать версию протокола в каждый пакет для обратной совместимости.

```go
type PacketHeader struct {
    Version uint8   // Версия протокола
    Magic   uint16
    Type    uint8
    Length  uint16
}
```

**Стратегии:**
- **Мажорная версия:** Несовместимые изменения (ломающие изменения)
- **Минорная версия:** Совместимые изменения (новые поля, расширения)

## 🔄 Синхронизация состояния

### 1. Authority и Ownership

**Authority (Авторитет):**
- Сервер является источником истины для состояния игры
- Клиенты отправляют команды, сервер обрабатывает и рассылает обновления

**Ownership (Владение):**
- Клиент "владеет" своим персонажем (отправляет команды)
- Сервер валидирует и применяет изменения

### 2. Техники синхронизации

#### Client-Side Prediction (Клиентское предсказание)

**Описание:** Клиент предсказывает результат своих действий до получения подтверждения от сервера.

**Преимущества:**
- Ощущение мгновенного отклика
- Сглаживание латентности для локальных действий

**Недостатки:**
- Нужна система отката (rollback) при рассинхронизации
- Сложнее реализация

**Пример:**
```
Клиент: Отправляет команду движения → Предсказывает позицию
Сервер: Обрабатывает команду → Отправляет подтверждение
Клиент: Корректирует позицию при рассинхронизации
```

#### Server Reconciliation (Серверная реконцилиация)

**Описание:** Сервер отправляет подтверждения команд с номерами последовательности.

**Процесс:**
1. Клиент отправляет команду с sequence number
2. Сервер обрабатывает и подтверждает с тем же sequence number
3. Клиент корректирует свое состояние по подтверждению сервера

#### Entity Interpolation (Интерполяция сущностей)

**Описание:** Сглаживание движения других игроков через интерполяцию между полученными состояниями.

**Пример:**
```go
func InterpolatePosition(current, target Position, t float32) Position {
    return Position{
        X: Lerp(current.X, target.X, t),
        Y: Lerp(current.Y, target.Y, t),
    }
}
```

#### Lag Compensation (Компенсация задержки)

**Описание:** Сервер "откатывается" во времени при обработке действий (например, выстрела).

**Процесс:**
1. Клиент отправляет выстрел с временной меткой
2. Сервер откатывается к моменту выстрела
3. Проверяет попадание
4. Возвращается к текущему времени

### 3. Частота обновлений

**Рекомендации по частоте:**
- **Локальные команды:** Как можно чаще (60+ Hz)
- **Обновления состояния сервера:** 20-30 Hz для большинства игр
- **Критичные данные:** По требованию (instant)

**Оптимизация:**
- Адаптивная частота в зависимости от сетевых условий
- Приоритизация обновлений (близкие объекты чаще)

## ⚡ Компенсация латентности

### 1. Измерение латентности

**RTT (Round Trip Time):**
- Время отправки пакета и получения ответа
- Измеряется через ping/pong сообщения

**One-Way Latency:**
- Приблизительная оценка через timestamp в пакетах

### 2. Адаптивные техники

#### Dynamic Tick Rate

**Описание:** Адаптация частоты обновлений в зависимости от латентности.

```go
func CalculateTickRate(latency time.Duration) time.Duration {
    if latency > 100*time.Millisecond {
        return 20 * time.Millisecond // 50 Hz
    }
    return 16 * time.Millisecond // 60 Hz
}
```

#### Adaptive Dead Reckoning

**Описание:** Адаптация предсказания движения в зависимости от сетевых условий.

#### Buffering и Jitter Handling

**Описание:** Буферизация пакетов для сглаживания неравномерной доставки.

## 🔒 Безопасность и валидация

### 1. Server-Side Validation (Серверная валидация)

**Принцип:** Никогда не доверяйте клиенту.

**Что валидировать:**
- Позиция игрока (физически возможные перемещения)
- Скорость и ускорение
- Время между действиями (cooldown)
- Ресурсы и очки
- Дальность действия (выстрел, взаимодействие)

**Пример:**
```go
func ValidateMovement(serverPos, clientPos Position, dt time.Duration, maxSpeed float32) bool {
    distance := Distance(serverPos, clientPos)
    maxDistance := maxSpeed * float32(dt.Seconds())
    
    // Учитываем погрешность сети
    tolerance := maxDistance * 0.2
    
    return distance <= maxDistance + tolerance
}
```

### 2. Античит техники

#### Rate Limiting

**Описание:** Ограничение частоты команд от одного клиента.

```go
type RateLimiter struct {
    commands    map[ClientID][]time.Time
    maxCommands int
    window      time.Duration
}

func (r *RateLimiter) CanExecute(clientID ClientID) bool {
    now := time.Now()
    // Проверка количества команд в окне времени
    // ...
}
```

#### Sanity Checks

**Описание:** Проверка на недопустимые значения.

- Максимальная скорость
- Максимальный урон
- Допустимый диапазон координат
- Валидность действий (возможность выполнить действие)

#### Server Replay

**Описание:** Воспроизведение действий сервера для анализа подозрительного поведения.

### 3. Криптография и защита данных

#### Шифрование

- **TLS/SSL** для TCP соединений
- **DTLS** для UDP соединений
- Шифрование критичных данных (пароли, платежи)

#### Защита от модификации пакетов

- HMAC подписи для критичных команд
- Checksums для обнаружения ошибок передачи

## 📊 Оптимизация трафика

### 1. Сжатие данных

#### Delta Compression (Дельта-сжатие)

**Описание:** Отправка только изменений вместо полного состояния.

```go
type DeltaState struct {
    EntityID  uint32
    ChangedFields []Field
}

// Вместо полного состояния отправляем только измененные поля
```

#### Bit Packing

**Описание:** Упаковка данных в биты для минимизации размера.

```go
// Вместо uint8 для направления (0-3), используем 2 бита
direction := (packet >> 6) & 0x03
```

### 2. Приоритизация данных

**Категории:**
- **Critical:** Критичные данные (смерть игрока, конец игры) — отправляются немедленно
- **High:** Важные обновления (позиция, видимость) — высокая частота
- **Medium:** Обновления состояния — средняя частота
- **Low:** Метаданные — низкая частота или по требованию

### 3. Пространственная оптимизация

**Описание:** Отправка обновлений только для видимых/близких объектов.

**Relevance List:**
- Определение списка релевантных объектов для каждого клиента
- Обновления только для релевантных объектов

### 4. Сжатие сетевых пакетов

**Техники:**
- **gzip/deflate** для текстовых данных
- **Специализированные алгоритмы** для игровых данных
- **Словарное сжатие** для повторяющихся паттернов

## 🎯 Рекомендации для Gonflict

### Текущее состояние

- ✅ **Локальная игра:** Все действия обрабатываются локально
- ✅ **AI через Lua:** Гибкая система AI для врагов

### Возможные улучшения для сетевой версии

1. **Локальный мультиплеер (P2P):**
   - UDP протокол для обмена состояниями танков
   - Простая синхронизация через snapshot каждые 100ms
   - Подходит для локальной сети (LAN)

2. **Онлайн мультиплеер:**
   - Клиент-серверная архитектура
   - Server authority для валидации действий
   - Client-side prediction для локальных действий
   - 20-30 Hz обновления состояния

3. **Оптимизации:**
   - Delta compression для карты (отправка только изменений блоков)
   - Приоритизация: танки > пули > анимации
   - Пространственная оптимизация (игрок видит только близкие объекты)

## 📝 Примечания

- Для большинства игр рекомендуется **Client-Server** архитектура с **UDP** для игровых обновлений и **TCP** для критичных команд
- **Server-side validation** критично для предотвращения читов
- **Client-side prediction** значительно улучшает ощущение от игры при наличии задержки
- Профилирование сетевого трафика важно для оптимизации
- Тестирование на различных сетевых условиях (высокая латентность, потеря пакетов) обязательно

**Примечание:** Реализация сетевых протоколов для игр — это сложная задача, требующая баланса между производительностью, надежностью и безопасностью. Начните с простой реализации и итерируйте, добавляя оптимизации по мере необходимости.
